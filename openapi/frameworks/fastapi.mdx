## Introduction to FastAPI and OpenAPI

Understanding how FastAPI generates OpenAPI documents supports informed decisions when customizing a FastAPI setup.

The process is straightforward: FastAPI builds the OpenAPI document from application routes and models. Each route adds an operation to the OpenAPI document. Each model used by these routes adds a schema definition. Request and response bodies, parameters, and headers draw from these schema definitions.

While this process works well out of the box, FastAPI also offers several customization options that can change the generated OpenAPI document. The following sections cover several options.

## The FastAPI example app: Train Travel API

The example FastAPI application is following the common Train Travel API, which includes models for stations, trips, bookings, and payments, and provides operations for finding trips and managing bookings.

The guide examines how this FastAPI application uses refined models and routes to produce an intuitive OpenAPI document. The schema also supports SDK generation with Speakeasy. Source code is available in the [framework-fastapi](https://github.com/speakeasy-api/examples/tree/main/framework-fastapi) folder of the Speakeasy Examples repository.

The `framework-fastapi` directory consists of two directories: `app` and `sdk`.

The `app` directory contains the FastAPI server definition: `app/main.py`, including the customizations described in this guide.

The `sdk` directory and the two OpenAPI documents, `openapi.yaml` and `openapi.json`, are generated by running `gen.sh` in the root of the project.

The following sections explain how FastAPI customization can streamline SDK generation.


## Basic FastAPI setup

The basics provide a foundation for the remaining examples.

### Scalar API documentation

FastAPI automatically generates API documentation using Swagger UI. This example also has [Scalar](https://scalar.com/) API documentation. Scalar is an alternative to Swagger UI. Its standout feature, as explained in the Speakeasy blog post, [Choosing a docs vendor: Mintlify vs Scalar vs Bump vs ReadMe vs Redocly](https://www.speakeasy.com/blog/choosing-a-docs-vendor#mintlify-seriously-beautiful-docs), is that it can be used as a standalone API client. Scalar is also easy to use and has a modern UI that can be customized to create branded documentation. Scalar also powers [Speakeasy docs](https://www.speakeasy.com/blog/release-speakeasy-docs#why-we-partnered-with-scalar).

Scalar is added to the FastAPI app by installing the [Scalar FastAPI plugin](https://github.com/scalar/scalar/blob/main/integrations/fastapi/README.md).

After installing the plugin, add a `/scalar` route in `app/main.py` to return the Scalar API Reference:

```python
from scalar_fastapi import get_scalar_api_reference

# ...

app = FastAPI()

# ...

@app.get("/scalar", include_in_schema=False)
async def scalar_html():
    return get_scalar_api_reference(
        openapi_url=app.openapi_url,
        title=app.title + " - Scalar",
    )

```

### Server configuration

While working with FastAPI in development, generated docs, the development server, and API operations work out of the box without manually specifying a server address.

When generating SDKs, the OpenAPI document needs to list servers.

A common convention is to pop in the local and production servers (local can be stripped out with [overlays](https://www.speakeasy.com/openapi/overlays) later if they are not wanted showing up on live documentation) are configured in `app/main.py` as follows:

```python
from fastapi import FastAPI

app = FastAPI(
    servers=[
    {"url": "http://localhost:8080", "description": "Local Server"},
    {"url": "https://api.example.com", "description": "Production"},
    ],
)
```

This leads to the following generated output in `openapi.yaml`:

```yaml
# The basic server configuration in OpenAPI
servers:
  - description: Local Server
    url: http://localhost:8080
  - description: Production
    url: https://api.example.com
```

### Typed responses

SDK users may want to see all possible responses for an API call.

FastAPI supports additional responses on each route through response types.

The following abbreviated code belongs in `app/main.py`:

```python
from fastapi import FastAPI
from fastapi.responses import JSONResponse
from pydantic import BaseModel, Field

class ResponseMessage(BaseModel):
    """A response message"""

    message: str = Field(description="The response message")

OPENAPI_RESPONSE_STATION_NOT_FOUND = {
    "model": ResponseMessage,
    "description": "Station not found",
}

def response_station_not_found(station_id: int):
  """Response for station not found"""

    return JSONResponse(
        status_code=404,
        content=f"Station with id {station_id} does not exist",
    )

class Station(BaseModel):
    id: int
    name: str
    description: str = None

app = FastAPI()

@app.get(
    "/stations/{station_id}",
    response_model=Station,
    responses={404: OPENAPI_RESPONSE_STATION_NOT_FOUND},
    tags=["Stations"],
)
  def get_station(station_id: Annotated[int, Path(title="Station ID")]):
    """Read a station"""

    for station in stations_db:
      if station.id == station_id:
        return station
    return response_station_not_found(station_id)
```

FastAPI adds a schema for the specific error message to `openapi.yaml`:

```yaml
components:
  schemas:
    ResponseMessage:
      description: A response message
      properties:
        message:
          description: The response message
          title: Message
          type: string
      required:
        - message
      title: ResponseMessage
      type: object
```

### Operation tags

As an API develops and grows, routes are often split into separate files. FastAPI [provides conveniences](https://fastapi.tiangolo.com/tutorial/bigger-applications/) to reduce boilerplate and repetition when splitting an API into multiple modules.

This separation may reduce cognitive overhead during work on particular sections of API code, but similar groups are not automatically created in documentation and SDK code.

Add tags to all operations in FastAPI, whether the application is large or contains only a handful of operations, so that operations can be grouped by tag in generated SDK code and documentation.

```yaml filename="operation-tags.yaml"
# Tags help organize operations into logical groups
tags:
  - name: Stations
    description: Find and filter train stations across Europe.
  - name: Trips
    description: Timetables and routes for train trips between stations.
  - name: Bookings
    description: Create and manage bookings for train trips.
  - name: Payments
    description: Pay for bookings and view payment status.
```

The most straightforward way to add tags is to edit each operation and add a list of tags. This example highlights the tags list:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get(
    "/stations",
    tags=["Stations"],
)
  def get_stations():
    return {
      "data": [],
    }
```

### Tag metadata

Tag metadata can further improve the developer experience.

FastAPI accepts an `openapi_tags` parameter for metadata such as a description and a list of external documentation links.

Here's how to add metadata to tags:

```python
from fastapi import FastAPI

tags_metadata = [
    {
        "name": "Stations",
        "description": "Find and filter train stations across Europe.",
        "externalDocs": {
            "description": "Train station external docs",
            "url": "https://en.wikipedia.org/wiki/Train_station",
        },
    },
    {
        "name": "Trips",
        "description": "Timetables and routes for train trips between stations.",
    )
]

app = FastAPI(
    openapi_tags=tags_metadata,
)

app = FastAPI(
    openapi_tags=tags_metadata,
)

@app.get(
    "/trips",
    tags=["Trips"],
)
  def get_trips():
    return {
      "data": [],
    }
```

When metadata is added to tags, FastAPI adds a top-level `tags` section to the OpenAPI document:

```yaml
tags:
  - description: Find and filter train stations across Europe.
    externalDocs:
      description: Train station external docs
      url: https://en.wikipedia.org/wiki/Train_station
    name: Stations
  - description: Timetables and routes for train trips between stations.
    name: Trips
```

Each tagged path in the OpenAPI document also gets a list of tags:

```yaml
paths:
  /trips:
    get:
      description: Find available trips
      operationId: get-trips
      summary: Get Trips
      tags:
        - Trips
      # ...
```

### Operation ID customization

```python
def generate_unique_id(route: "APIRoute") -> str:
    operation_id = route.name + route.path_format
    operation_id = re.sub(r"\W", "_", operation_id)
    assert route.methods
    operation_id = operation_id + "_" + list(route.methods)[0].lower()
    return operation_id
```

This can often lead to cumbersome and unintuitive names. Two methods are available for customizing these generated strings:

1. Using a custom `generate_unique_id_function`
2. Specifying `operation_id` per operation

The preferred method is a custom function for generating unique IDs for paths.

The following illustrative function does not generate guaranteed-unique IDs or handle method names without an underscore. It demonstrates how a function can generate IDs based on an operation's method name:

```python
from fastapi import FastAPI

def convert_snake_case_to_camel_case(string: str) -> str:
    """Convert snake case to camel case"""

    words = string.split("_")
    return words[0] + "".join(word.title() for word in words[1:])


def custom_generate_unique_id_function(route: APIRoute) -> str:
    """Custom function to generate unique id for each endpoint"""

    return convert_snake_case_to_camel_case(route.name)


app = FastAPI(
    generate_unique_id_function=custom_generate_unique_id_function,
)
```

FastAPI also supports specifying the `operationId` per operation. The following example adds an `operation_id` parameter to the operation decorator:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get(
    "/trips",
    operation_id="get-trips",
)
  def get_trips():
    pass
```

### Webhooks

Starting with OpenAPI version 3.1.0, applications can specify webhooks in OpenAPI.

Here's how to add a webhook to FastAPI:

```python
from fastapi import FastAPI

app = FastAPI()


class Booking(BaseModel):
    id: int
    note: str


@app.webhooks.post(
    "booking-status-changed",
    operation_id="webhookBookingStatusChanged",
)
  def webhook_booking_status_changed(body: Booking):
    """
    When a booking status is changed, this webhook will be triggered.

    The server will send a `POST` request with the booking details to the webhook URL.
    """
    pass
```

FastAPI generates the following top-level `webhooks` section in `openapi.yaml`:

```yaml
webhooks:
  booking-status-changed:
    post:
      description:
        "When a booking status is changed, this webhook will be triggered.


        The server will send a `POST` request with the booking details to the webhook
        URL."
      operationId: webhookBookingStatusChanged
      requestBody:
        content:
          application/json:
            schema:
              $ref: "#/components/schemas/Booking"
        required: true
      responses:
        "200":
          content:
            application/json:
              schema: {}
          description: Successful Response
        "422":
          content:
            application/json:
              schema:
                $ref: "#/components/schemas/HTTPValidationError"
          description: Validation Error
      summary: Webhook Booking Status Changed
```

Adding the server information leads to the following generated output in the `openapi.yaml` file:

```yaml
# This server configuration will be used by Speakeasy when generating SDKs
openapi: 3.1.0

  title: Train Travel API
  version: 1.2.1
servers:
  - description: Local Server
    url: http://localhost:8080
```

After Speakeasy generates the SDK, this leads to the following abbreviated code in `sdk/src/openapi/sdkconfiguration.py`:

```python
from dataclasses import dataclass

SERVERS = [
  'http://localhost:8080',
  # Local Server
]
"""Contains the list of servers available to the SDK"""

@dataclass
class SDKConfiguration:
    ...
    server_url: Optional[str] = ""
    server_idx: Optional[int] = 0
    ...

    def __post_init__(self):
        self._hooks = SDKHooks()

    def get_server_details(self) -> Tuple[str, Dict[str, str]]:
        if self.server_url is not None and self.server_url:
            return remove_suffix(self.server_url, "/"), {}
        if self.server_idx is None:
            self.server_idx = 0

        return SERVERS[self.server_idx], {}
```

Calls to `SDKConfiguration.get_server_details()` appear when the SDK builds API URLs:

```python

]
"""Contains the list of servers available to the SDK"""
```

Speakeasy uses the title, summary, and descriptions from the document to add helpful text to generated SDK documentation, including comments in SDK code. For example, in `sdk/src/openapi/sdk.py`:

```python
class SDK(BaseSDK):
    r"""Train Travel API: Find and book train trips across Europe

    API for finding and booking train trips across Europe.
    """
```

Speakeasy adds the version to the `SDKConfiguration` in `sdk/src/openapi/sdkconfiguration.py`. It also uses this version to construct the user agent (`user_agent`), which contains the version of the SDK, the version of the Speakeasy generator build, and the version of the OpenAPI documentation:

```python
from dataclasses import dataclass

@dataclass
class SDKConfiguration:
    ...
    openapi_doc_version: str = '1.2.1'
    user_agent: str = "speakeasy-sdk/python 0.2.0 2.607.0 1.2.1 openapi"
    ...
```

When an API is called using the generated SDK, the `user_agent` from `SDKConfiguration` is automatically added to the `user-agent` header. The `_build_request_with_client` method in `BaseSDK` constructs the HTTP request and sets the header using `headers[user_agent_header] = self.sdk_configuration.user_agent`:

```python
def _build_request_with_client(
    self,
    ...
    user_agent_header,
    ...
) -> httpx.Request:
    ...
    headers["Accept"] = accept_header_value
    headers[user_agent_header] = self.sdk_configuration.user_agent
    ...
```

### Operation ID issues and solutions

The unique `operation_id` generated by FastAPI does not translate well into an SDK. Customize the generated `operation_id` for better readability.

For instance, in the operation that returns a station by `station_id`, the default unique ID would be `read_station_stations__station_id__get`. This makes its way into SDK code, leading to class names such as `ReadStationStationsStationIDGetRequest` or function names like `read_station_stations_station_id_get`.

Here's a usage example after generating an SDK without customizing the `operationId`:

```python
import sdk
from sdk.models import operations

s = sdk.SDK()

req = operations.ReadStationStationsStationIDGetRequest(
  station_id=847252,
)

res = s.stations.read_station_stations_station_id_get(req)
```

After applying the previously defined `generate_unique_id` function, the `get_station` operation receives the friendlier `getStation` operation ID, making the usage example easier to read:

```python
import sdk
from sdk.models import operations

s = sdk.SDK()

req = operations.GetStationRequest(
  station_id=847252,
)

res = s.stations.get_station(req)
```

In addition to the two methods described earlier, a third way to customize the `operation_id` is available. Add the top-level `x-speakeasy-name-override` [Speakeasy extension](https://www.speakeasy.com/docs/speakeasy-reference/extensions) to the OpenAPI document, allowing Speakeasy to override generated names during SDK generation.
To add this extension, follow the Speakeasy guide to [changing method names](/docs/customize-sdks/methods).

```yaml filename="name-override.yaml"
# Example of x-speakeasy-name-override extension
x-speakeasy-name-override:
  operations:
    getStation: getStationDetails
    createBooking: addBooking
```

### Adding retry functionality

Speakeasy can generate SDKs that follow custom rules for retrying failed requests. For instance, if a server fails to return a response within a specified time, retrying the request can avoid unnecessary load.

To add retries to SDKs generated by Speakeasy, add a top-level `x-speakeasy-retries` schema to the OpenAPI document. The retry strategy can also be overridden per operation by adding `x-speakeasy-retries` to each operation:

```yaml filename="speakeasy-retries.yaml"
# Speakeasy retries can be configured with a top-level extension
x-speakeasy-retries:
  strategy: backoff
  statusCodes: [5XX]
  retryConnectionErrors: true
```

To add global retries, customize the schema generated by the FastAPI `get_openapi` function:

```python
from fastapi import FastAPI
from fastapi.openapi.utils import get_openapi

app = FastAPI(
    summary="Find and book train trips across Europe",
    description="API for finding and booking train trips across Europe.",
    version="1.2.1",
    title="Train Travel API",
)

def custom_openapi():
    if app.openapi_schema:
        return app.openapi_schema

    openapi_schema = get_openapi(
        title=app.title,
        version=app.version,
        summary=app.summary,
        description=app.description,
        routes=app.routes,
    )

    # Add retries
    openapi_schema["x-speakeasy-retries"] = {
        "strategy": "backoff",
        "backoff": {
            "initialInterval": 500,
            "maxInterval": 60000,
            "maxElapsedTime": 3600000,
            "exponent": 1.5,
        },
        "statusCodes": [
            "5XX",
        ],
        "retryConnectionErrors": True,
    }

    app.openapi_schema = openapi_schema
    return app.openapi_schema


app.openapi = custom_openapi
```

Add this customization _after_ declaring the operation routes.

This change adds the following top-level section to `openapi.yaml`:

```yaml
x-speakeasy-retries:
  backoff:
    exponent: 1.5
    initialInterval: 500
    maxElapsedTime: 3600000
    maxInterval: 60000
  retryConnectionErrors: true
  statusCodes:
    - 5XX
  strategy: backoff
```

To add `x-speakeasy-retries` to a single operation, update the operation and add the `openapi_extra` parameter as follows:

```python
from fastapi import FastAPI

app = FastAPI()

@app.get(
    "/bookings",
    openapi_extra={
        "x-speakeasy-retries": {
            "strategy": "backoff",
            "backoff": {
                "initialInterval": 500,
                "maxInterval": 60000,
                "maxElapsedTime": 3600000,
                "exponent": 1.5,
            },
            "statusCodes": [
                "5XX",
            ],
            "retryConnectionErrors": True,
        }
    },
)
def list_bookings():
    return []
```

### Authentication and security

FastAPI supports several authentication mechanisms that can easily be integrated into your API.

The following example adds an API key authentication scheme to the `/bookings` endpoint. The `APIKeyHeader` dependency validates the API key passed in the `Authorization` header:

```python
from fastapi.security import APIKeyHeader

API_KEY = "your-train-travel-api-key"

header_scheme = APIKeyHeader(
    name=API_KEY,
    auto_error=True,
    description="API Key for the booking API. API Key should be sent as a header, with the value 'your-train-travel-api-key'",
    scheme_name="api_key",
)
```

Pass a `key` parameter to the `list_bookings` function to retrieve and validate the API key from the header:

```python
@app.get(
    "/bookings",
    response_model=List[Booking],
    tags=["Bookings"],
    ...
)
def list_bookings(key: str = Depends(header_scheme)):
  """List all bookings"""

    if key != API_KEY:
        raise HTTPException(status_code=401, detail="Invalid API Key")

    return [Booking(**booking_data.dict()) for booking_data in bookings_db]
```

Now when generating the OpenAPI document, the API key authentication scheme will be included and only required for the listing on the `/bookings` endpoint.

### Handling form data

Form data is a common way to receive information from clients, particularly in web applications. FastAPI provides robust support for form data through its `Form` class, and it correctly documents these form fields in the OpenAPI schema.

When working with form data in FastAPI, use the `Form` class from the `fastapi` module. This ensures that FastAPI adds the appropriate schema information to the OpenAPI document.

```python
from fastapi import FastAPI, Form
from typing import Annotated

app = FastAPI()

@app.post("/bookings/create/")
async def create_booking_form(
    name: Annotated[str, Form()],
    description: Annotated[str, Form()],
    price: Annotated[float, Form()]
):
    """Create a new booking using form data"""
    return {
        "name": name,
        "description": description,
        "price": price
    }
```

In the OpenAPI document, FastAPI correctly identifies this endpoint as accepting form data:

```yaml
paths:
  /bookings/create/:
    post:
      summary: Create Booking Form
      operationId: createBookingForm
      requestBody:
        content:
          application/x-www-form-urlencoded:
            schema:
              type: object
              properties:
                name:
                  type: string
                description:
                  type: string
                price:
                  type: number
              required:
                - name
                - description
                - price
      responses:
        "200":
          description: Successful Response
          content:
            application/json:
              schema: {}
      tags:
        - Bookings
```

When Speakeasy generates an SDK from this OpenAPI document, it will correctly handle form data submissions. The generated SDK will provide a clean interface for submitting form data:

```python
import sdk
from sdk.models import operations

s = sdk.SDK()

req = operations.CreateBookingFormRequest(
  name="John Doe",
  description="Booking for a train trip",
    price=8.99
)

res = s.bookings.create_booking_form(req)
```

#### File uploads

FastAPI also supports file uploads, both as individual files or as multiple files. The OpenAPI schema will correctly document these endpoints as accepting multipart form data.

```python
from fastapi import FastAPI, File, UploadFile
from typing import Annotated

app = FastAPI()

@app.post("/bookings/document/")
async def upload_booking_document(
  booking_id: Annotated[int, Form()],
    image: Annotated[UploadFile, File()]
):
    """Upload a document for a booking"""
    contents = await image.read()
    # Process file contents...
    return {
        "booking_id": booking_id,
        "filename": image.filename,
        "content_type": image.content_type,
        "size": len(contents)
    }
```

This endpoint will be documented in the OpenAPI schema with `multipart/form-data` content type, allowing Speakeasy to generate appropriate SDK code for handling file uploads.

#### Advanced form validation

For form data requiring validation beyond simple type checking, combine Pydantic models with the `Form` class. First, define the model with validation rules:

```python
from pydantic import BaseModel, Field

class BookingFormData(BaseModel):
    name: str = Field(..., min_length=3, max_length=50)
    description: str = Field(..., min_length=10, max_length=200)
    price: float = Field(..., gt=0, le=100)
```

Then use the model fields with form data:

```python
@app.post("/bookings/create/validated/")
async def create_booking_validated(
    name: Annotated[str, Form()],
    description: Annotated[str, Form()],
    price: Annotated[float, Form()]
):
    booking_data = BookingFormData(
        name=name,
        description=description,
        price=price
    )
    return booking_data
```

FastAPI will generate an OpenAPI document that includes these validation constraints, allowing SDK users to understand the requirements before submitting the form.
