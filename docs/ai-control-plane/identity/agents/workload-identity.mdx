Workload identity lets a CI job, Kubernetes pod, Claude Tag channel, or other workload connect to MCP servers without a stored secret. The workload presents the identity token its own platform already issues, such as a GitHub Actions OIDC token, and exchanges it for a short-lived Speakeasy access token. The workload then acts as the agent assigned to it and inherits that agent's policy in full.

## Access requirements

<Callout type="info">
  Managing the Access Hub requires `workload:read` to view it and `workload:write` to change it. Only the Admin role holds both by default. Choosing an agent for a workload requires no permission on the agent itself, so grant `workload:write` only to people trusted to hand any agent's access to a machine.
</Callout>

## When to use workload identity

Choose the credential that fits where the agent runs:

| | API key | Workload identity |
| --- | --- | --- |
| Runs in | Any runtime | Runtimes whose platform issues identity tokens, such as Claude Tag, GitHub Actions, Kubernetes, and SPIFFE |
| Secret to store | Yes, the key | None |
| Token lifetime | Up to one year, revocable | 15 minutes, with no refresh token |
| Servers with per-user OAuth | The key owner's connected account | The agent owner's connected account |

Workload identity removes the risk of a leaked long-lived key. Use an [API key](/docs/ai-control-plane/identity/agents/authorizing-agents#create-an-agent) for laptops, hosted agents, and any runtime without a platform identity token.

## How it works

Three pieces of configuration decide whether a workload gets in and what it can do:

- **Trusted platform**: an issuer whose tokens Speakeasy verifies, identified by its issuer URL and the URL of its signing keys (JWKS URI). Trusting a platform admits nothing on its own.
- **Access rule**: a token subject, the `sub` claim, that is allowed to sign in, and the agent it acts as. A rule matches one subject exactly, or every subject that starts with a prefix when it ends in `*`.
- **Agent**: supplies the whole policy the workload acts under. The workload holds no permissions of its own, and it can reach only what both the agent's policy and the agent owner's current permissions allow. If the owner loses access to a server, the workload loses it on its next request.

A workload is admitted only when its token is signed by a trusted platform and its subject matches an access rule under that platform. Platforms such as Anthropic, GitHub, and Google sign tokens for all of their customers, so a valid signature alone proves nothing. The access rule is the security boundary.

The workload sends its platform token to the token endpoint of a Speakeasy authorization server and receives an access token valid for 15 minutes. It sends that access token as a bearer token on MCP requests. There's no refresh token: when the access token expires, the workload exchanges a fresh platform token.

## Manage the Access Hub

The [Access Hub](https://ai.speakeasy.com/@self/access-hub) lists the platforms the organization trusts and the access rules under each one. Open it from the organization sidebar under **Secure > Access Hub**. Trust applies to MCP servers in every project.

The Access Hub has two tabs:

- **Catalog**: platforms Speakeasy has verified, with their issuer and signing keys already filled in. Selecting one opens a guided setup that asks only for what differs per organization. To connect Claude Tag, follow [Connect Claude Tag channels with workload identity](/docs/ai-control-plane/guides/claude-tag-workload-identity).
- **Custom**: any other platform, registered by hand.

### Register a custom platform

On the **Custom** tab, select **Register new access** and fill in:

- **Name**: how the platform is labeled in the Access Hub. Not used for matching.
- **Issuer**: the value the token's `iss` claim must carry. It must be an HTTPS URL. Speakeasy stores it exactly as entered, so copy it from the platform's documentation or discovery document.
- **JWKS URI**: where the platform publishes its signing keys. It must be an HTTPS URL.
- **Description** and **Tags**: optional, for finding the platform later.

Select **Register**. The issuer is fixed once registered. To trust a different issuer, register it as a new platform.

### Allow access

Open the platform, select **Allow access**, and fill in:

- **Subject**: the `sub` claim to admit, compared exactly as entered. To admit every subject that starts with the same text, end the subject with `*`.
- **Agent**: the agent the workload acts as. Choose the most narrowly scoped agent that can do the job.
- **Label** and **Tags**: optional. A label helps when a subject is opaque, such as a numeric service account ID.

Select **Allow access**.

<Callout title="Use a wildcard only where the platform controls the varying part" type="warning">
  A rule ending in `*` admits every subject that starts with the text before it, including subjects created later. That's safe when the platform mints the varying part, as Anthropic does with agent IDs in `wimse://identity.anthropic.com/org/ORG_ID/agent/*`. It isn't safe when the caller influences the subject. For example, `repo:acme/deploy:*` on GitHub Actions admits every branch, so anyone who can push a branch gets in.
</Callout>

A rule for an exact subject takes priority over a wildcard rule that also matches it, and a longer wildcard takes priority over a shorter one. This makes it possible to admit a whole fleet under one agent and give a single workload a different one.

### Change or remove access

Select the **⋮** menu on a rule to edit its agent, label, or tags, or to remove it. The subject is fixed once allowed. To stop trusting a platform and every rule under it, select **Stop trusting** on the platform.

Removing access doesn't end sessions already issued. To stop a workload immediately, also revoke its sessions on [MCP Sessions](/docs/ai-control-plane/mcp-gateway/access/clients-and-sessions#organization-wide-view), or [suspend the agent](/docs/ai-control-plane/identity/agents#suspend-revoke-or-delete-an-agent). Every change to platforms and access rules is recorded in [Audit Logs](/docs/ai-control-plane/org-admin/audit-logs).

## Exchange a platform token

A workload exchanges its token at the token endpoint of a shared Speakeasy authorization server, which serves every MCP server attached to it. Organization admins find each authorization server's issuer URL and token endpoint under **Speakeasy Authorization Servers** in the organization settings.

<Callout type="info">
  Workload sign-in needs an authorization server in shared mode. If none is listed, contact Speakeasy to enable one for the organization or a project.
</Callout>

Request a token from the platform with its audience set to the authorization server's issuer URL. Then post it to the token endpoint using the OAuth JWT bearer grant:

```bash
curl https://AUTHENTICATION_HOST/oauth/usi/ISSUER_ID/token \
  --data-urlencode "grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer" \
  --data-urlencode "assertion=$PLATFORM_TOKEN" \
  --data-urlencode "resource=https://MCP_HOST/mcp/SERVER_SLUG"
```

No client ID or secret is involved. The `resource` parameter is optional:

- With `resource`, the access token works only at that MCP server.
- Without it, the access token works at every MCP server of the authorization server that the agent may connect to.

A successful exchange returns the access token:

```json
{
  "access_token": "eyJ...",
  "token_type": "Bearer",
  "expires_in": 900
}
```

Send it as `Authorization: Bearer ACCESS_TOKEN` on MCP requests. When it expires or is revoked, the MCP server answers `401` with `error="invalid_token"`, and the workload exchanges a fresh platform token. Use a new platform token for each exchange, because a token with a `jti` claim is accepted only once.

Every refusal returns the same `invalid_grant` error, so callers can't probe the trust policy. A `resource` that isn't an MCP server of the authorization server returns `invalid_target`.

## Servers with per-user OAuth

Some MCP servers call an upstream service with each person's own connected account. A workload has no person behind it, so it uses the account connected by the owner of its assigned agent. If the owner hasn't connected an account for that service, calls to the server fail rather than fall back to another credential.
