The **Shadow MCP** page inventories MCP servers discovered in agent traffic that aren't managed by the platform, meaning servers members connected on their own. Open it from **Secure > Shadow MCP** in the dashboard.

Shadow MCP detection depends on an active shadow MCP policy. A status indicator on the page shows whether one is scanning and links to [Guardrails](/docs/ai-control-plane/secure/guardrails) if not.

## Access requirements

<Callout type="info">
  Viewing this page requires the `org:admin` scope. Access is included in the
  [default Admin role](/docs/ai-control-plane/org-admin/roles-and-permissions)
  but not the Member role.
</Callout>

Managing allow rules additionally requires an enabled blocking shadow MCP policy in the project. Without one, the allow rule actions stay disabled and the page reports that an enabled blocking Shadow MCP policy is required.

## How servers are discovered

Every MCP-routed tool call in an instrumented agent session records which server it resolved to. The shadow MCP scanner replays that provenance for each call and classifies it:

- Calls that resolve to a platform-hosted MCP host are clean, including hosts on a [custom domain](/docs/ai-control-plane/org-admin/custom-domain) registered to the organization.
- Calls that resolve to anything else are flagged as shadow MCP. That covers third-party remote server URLs and local stdio servers launched by a command on the machine of the member.

Codex's built-in MCP resource tools (`list_mcp_resources`, `list_mcp_resource_templates`, and `read_mcp_resource`) name their target server in the call input rather than in the tool name. The scanner resolves that name against the MCP server inventory the session reports, so these calls face the same policy, and a target that cannot be resolved to a platform-hosted server is treated as shadow.

Classified calls carry a **Shadow MCP** source badge in [Tool Logs](/docs/ai-control-plane/observe/tool-logs), which is the per-call view behind the inventory. Filtering the log by that source shows exactly which calls the inventory was built from.

![Tool Logs filtered to the Shadow MCP source, with a Shadow MCP badge, tool name, user, and agent on each row](/assets/docs/ai-control-plane/secure/shadow-mcp-tool-logs.webp)

When provenance can't be resolved, because the hook event hasn't landed yet or the sender never resolved a server, the scanner falls back to checking the toolset identifier injected into hosted tool schemas. A call missing that identifier is treated as shadow.

Discovery therefore depends on agent sessions reaching the platform. Sessions from an uninstrumented client produce no traffic to scan. See [Device Agent](/docs/ai-control-plane/org-admin/device-agent) for how sessions are instrumented.

Servers are identified by canonical URL. Two members hitting the same server at different paths or with different query strings collapse to one inventory row.

## Policy status

The indicator at the top of the page reports what the active policy set does with a server that has no allow rule:

- **Blocking** — a blocking shadow MCP policy is enabled, and servers without allow rules are not allowed
- **Flagging** — only a flagging policy is enabled, so servers without allow rules are recorded but calls still succeed
- **No Policy** — no shadow MCP policy is enabled, and every discovered server is allowed

Flagging is the safe starting posture. It builds the inventory without interrupting anyone, which makes the allow list something to curate from real usage rather than guess at. See [Shadow MCP allow and block lists](/docs/ai-control-plane/guides/shadow-mcp-allow-and-block-lists) for the rollout sequence.

The status is driven by the shadow MCP policies in the project, which are created from [Guardrails](/docs/ai-control-plane/secure/guardrails). A policy that pairs the shadow MCP detector with the warn action produces the Flagging status:

![The review step of a risk policy showing the Shadow MCP detector, recommended scopes, a Warn action, medium severity, and an audience of Everyone](/assets/docs/ai-control-plane/secure/shadow-mcp-policy-review.webp)

## Inventory

The inventory table lists each discovered server with columns for the server name and URL, status, last called, last seen, and usage. Sorting and search operate across the full inventory, not only the loaded page.

![The Shadow MCP inventory listing discovered servers with their URLs, status, last called, last seen, and call and user counts](/assets/docs/ai-control-plane/secure/shadow-mcp-inventory.webp)

Each row carries one of five statuses:

- **Allowed** — an allow rule covers this URL
- **Blocked** — a blocking policy applies and no allow rule covers this URL
- **Observed** — seen in traffic, with no blocking policy applying to it
- **Pending** — at least one member has an unresolved access request for this server
- **Unknown** — the policy status could not be loaded

Pending takes precedence over the other statuses, so a server with an open request surfaces for review even when it already has an allow rule.

## Server detail

Opening a server shows its usage summary: pending requests, distinct users, allowed policies, observed use count, last called, last seen, and first seen. A **Top users** table ranks who uses the server, how many calls each has made, and when each last called it.

![A Shadow MCP server detail page with its status, request, user, and policy counts, usage timestamps, and a Top users table](/assets/docs/ai-control-plane/secure/shadow-mcp-server-detail.webp)

The **Add Allow Rule** button is disabled when no blocking policy is enabled, and the page says so directly beneath it.

Servers are named from their URL host by default. Rename a server inline from its detail page to give it something recognizable in the inventory. The rename sets a display label and does not change how the server is matched.

## Allow rules

An allow rule sanctions one server URL against one or more blocking shadow MCP policies. Calls to that URL then succeed for everyone the policy applies to.

Rules are managed from the row actions menu in the inventory or from the server detail page:

- **Add Allow Rule** — select which blocking policies should allow this server
- **Edit Rule** — change which policies allow it
- **Delete Rule** — remove the allow decision entirely

Each policy in the selector shows its audience, so a rule attached to a policy scoped to one role allows the server for that role only. An allow rule inherits the audience of the policy it attaches to and carries no audience of its own.

Deleting a rule also revokes any outstanding access requests for that URL.

<Callout type="info">
  Allowing a server is a stopgap, not a destination. A server worth sanctioning
  is usually worth bringing under management as a proper [tool
  source](/docs/ai-control-plane/reference/concepts/tool-sources), which puts
  its tools behind the same authentication, filtering, and logging as the rest
  of the platform.
</Callout>

## Access requests

When a blocking policy stops a call, the member sees the block reason along with a request access link. Opening the link signs them in and files a request against the policy that blocked the call. Links expire after seven days.

Requests surface in the inventory as a **Pending** status, and the row action becomes **Review Request**. Reviewing offers two outcomes:

- **Approve Request** — adds an allow rule for the selected policies and resolves the request
- **Deny Request** — resolves the request without granting access

The review panel shows the requester and the request date alongside the server URL, so the decision does not require leaving the page.

Approving here allows the server for everyone the selected policies apply to, not only the requester. To grant an exception to one person instead, resolve the request from the bypass queue on [Guardrails](/docs/ai-control-plane/secure/guardrails), which grants to named principals.

### Requesting access from the device agent

On machines running the [device agent](/docs/ai-control-plane/org-admin/device-agent), a blocked call also raises a desktop notification and adds the server to a **Blocked servers** card in the agent, so the request does not depend on the member noticing the link in the AI tool output. Confirming **Request access** files the same request against the blocking policy, and it lands in the inventory as **Pending** for review.

Only blocks that an approval can resolve prompt this way. A call stopped for PII or secrets raises no notification, because allowing the server would not unblock it.

Repeat blocks of the same server collapse into one entry rather than notifying again, and **Dismiss** suppresses that server on the device without sending anything to the platform. A denied request offers no retry, since running the blocked call again files a fresh one. On a device with no signed-in user, the agent opens the request page in a browser instead, which is the same flow as following the link in the AI tool output.
